# SaaS Starter 项目规划

## 1. 产品目标

把本仓库建设成一套**可复制、可裁剪、可验证的 SaaS 产品底座**。使用者从模板创建自己的产品时，复用通用的账号、权限、商业化和运营能力，把主要精力放在自己的产品业务上。

模板不是功能演示集合。每个标为可用的能力都应有明确的规格、服务端规则、API 契约、数据迁移、前端状态和可复现的验证方式。只有 UI 的页面要明确标为占位，不得当成已完成的业务能力。

首个完整版本面向单产品、单实例和个人用户。多租户和组织成员不是首版前置条件。部署平台当前暂缓，需等用户明确目标平台和交付要求后再规划。

## 2. 产品边界与架构分层

### 2.1 产品业务层

具体 SaaS 的业务功能。模板提供清楚的扩展位置和示例切片，但不预设某一种具体产品。业务代码放在 `apps/web/features/` 和 `services/api` 的业务模块中，并通过 OpenAPI 与 UI 通信。

### 2.2 SaaS 能力层

所有产品都可能复用的能力，按里程碑逐步实现：

- 账号、Session、账户生命周期和单实例角色权限。
- 套餐、订阅、订单、权益和用量计量。
- 邮件通知、后台管理、操作审计。
- 文件与异步任务（按实际需求加入）。
- 营销页面、定价、博客和文档入口。

### 2.3 基础设施与适配层

承载数据和外部服务，并为确有替换需求的供应商提供窄适配边界：

- PostgreSQL 是主数据库，迁移使用 `golang-migrate`；Better Auth schema 迁移遵循现有流程。
- OpenAPI 是 Web 与 Go API 之间的唯一契约来源，TypeScript Client 自动生成。
- 本地邮件捕获使用 Mailpit；生产邮件服务尚未选型。
- 支付、对象存储、任务队列、分析和监控服务尚未完成选型。
- 不为假设中的未来替换提前建设通用 Provider 框架。只有首个集成需求明确、或第二个实现确实出现时，再抽取稳定接口。

### 2.4 当前技术决策

| 能力 | 当前决定 | 规划原则 |
| --- | --- | --- |
| Web / BFF | Next.js App Router + TypeScript | 沿用现有 `apps/web` |
| 核心 API | Go + Gin | 业务授权、状态转换和数据访问以后端为准 |
| 契约 | OpenAPI + 生成的 TypeScript Client | 不手工修改生成代码 |
| 数据库 | PostgreSQL | 继续使用现有迁移体系；不引入 Drizzle 作为第二套数据层 |
| 认证 | Better Auth 邮箱认证 | 已完成；修改时更新既有规格与 ADR |
| UI | 当前 Next.js、Tailwind、shadcn/ui 代码 | 依现有组件体系演进，不另起一套 UI 技术栈 |
| 邮件、支付、文件、任务、部署 | 尚未选定或暂缓 | 由里程碑中的决策门槛确定，不视为已承诺供应商 |

## 3. 当前项目状态

### 已有基线

- 单仓库工程骨架、Next.js 页面结构、Gin API 服务和 PostgreSQL 迁移入口。
- OpenAPI 契约与 TypeScript Client 生成工作流。
- 邮箱密码注册、验证、登录、登出、忘记和重置密码、数据库 Session。
- `user` / `admin` 单实例角色，管理员提升命令，以及 Go API 的 JWT 验证和数据库授权检查。
- 本地 Mailpit、开发环境脚本、Go/Web 验证脚本和认证端到端 smoke 入口。
- 营销、认证、账户、Dashboard、管理后台、计费、用量、文件和任务等部分页面结构。除认证链路外，多个页面仍为占位或演示界面。

认证功能已完成，详见[邮箱认证功能规格](features/email-authentication.md)与[认证边界 ADR](decisions/0002-authentication-boundary.md)。本路线图不重复安排认证基础建设。

### 当前主要缺口

- GitHub Actions CI 工作流未建立；`.github/workflows/README.md` 仍记录为后续工作。
- 用户账户及管理员 UI 尚未形成完整的真实 API 业务链路。
- 计费、订阅、支付、权益和用量计量领域尚未实现。
- 集中式应用配置、错误约定、结构化日志和生产观测能力需要评估并补齐。
- 邮件生产服务、支付提供方、文件存储和部署平台尚未决策。
- 尚无从干净模板到真实产品业务的完整示例和复制说明。

## 4. 目标用户黄金路径

首版黄金路径限定在当前单实例范围内：

```text
复制仓库
  → 配置并校验环境变量
  → 安装依赖、启动本地服务、执行迁移
  → 运行检查并启动 Web / API
  → 注册、验证邮箱并登录
  → 进入个人账户 / Dashboard
  → 查看套餐并完成测试支付（支付能力交付后）
  → 服务端授予权益并限制或记录用量
  → 收到必要的账户与商业通知
  → 按产品团队选择的部署指南发布
```

当前部署环节暂缓；在部署平台选型和部署工作获准前，黄金路径的本地开发部分可以验收，不能宣称包含一键生产部署。首版不要求创建组织或 Workspace。

## 5. 版本与里程碑

版本是能力成熟度目标，里程碑是可单独验收的工作包。每个功能切片仍须先有 `specs/features/` 规格；跨模块领域规则写入 `specs/domain/`，架构或供应商选择写入 `specs/decisions/`。

### V0.1：可靠的个人开发底座

**整体状态：进行中。认证与工程骨架已完成，CI、账户管理和通用开发体验未完成。**

**目标**：新开发者能够在本地可靠启动、理解架构并验证改动；模板有安全的账号入口和最小平台管理能力。

**范围**：

- [已完成] Next.js + Gin + PostgreSQL 单仓库和 OpenAPI 生成流程。
- [已完成] 邮箱认证、Session、单实例 `user` / `admin` 和 Go 端授权。
- [x] GitHub Actions：契约/生成物一致性、Go 测试、Web lint、类型检查、构建；认证集成 smoke 视服务稳定性加入。
- [ ] 环境变量集中解析和校验；明确必需项、可选项和安全默认值。
- [ ] 统一 API 错误格式、请求关联 ID、结构化日志和健康检查；避免把认证凭据写入日志。
- [x] 个人账户页连接认证用户资料，提供姓名编辑；邮箱与角色不可通过资料表单修改。
- [x] 管理员用户页连接真实 API，提供最近用户和账号状态只读查询；账号状态修改仍未实现。
- [x] 更新干净 checkout 的安装、迁移、开发、验证和常见问题文档。

**前置依赖**：当前认证、OpenAPI、Makefile、`harness/scripts/` 和本地依赖服务。

**验收条件**：

- 新 PR 自动运行约定检查；CI 与本地 `make verify` 的范围一致，或明确记录差异。
- 干净 checkout 按 README 完成本地启动和验证，不依赖未记录的私有环境状态。
- 契约或生成物不一致、Go/Web 检查失败时，CI 能定位失败步骤。
- 账户及用户管理功能使用真实 API，权限由 Go 校验，不信任浏览器传入的角色或用户身份。
- 页面有加载、无数据和 API 失败状态；Web/API 错误可通过关联 ID 定位。

### V0.2：首个可替换的产品业务切片

**整体状态：进行中；个人任务示例已实现，输入边界和示例移除验收仍需补齐。支付与付费订阅不属于本阶段。**

**目标**：用一个范围受控的真实业务示例验证模板从规格到 UI 的完整开发路径，并明确模板能力与具体产品逻辑的边界。

**范围**：

- [x] 选择个人任务清单作为简单、可删除的示例用例，编写功能规格。
- [x] 实现数据迁移、用户归属的 Go CRUD API、OpenAPI、生成 Client 和 Next.js 页面。
- [x] 验证账户身份、服务端授权、空/错误/提交中状态和本地开发流程可复用。
- 只有示例业务确实需要时，才实现免费额度或简单权益；不预先构建完整订阅、支付或通用计费框架。

**前置依赖**：

- V0.1 账户、管理和验证闭环达到可用状态。
- 明确示例用例及其验收场景；如果尚无合适用例，先完成规格和设计，不实现臆造的业务功能。

**验收条件**：

- [x] 选定的示例可从数据库经 API 到 UI 完成创建、查询、完成/重开和删除流程。
- [x] 业务授权在 Go API 执行；用户 ID 来自已验签身份，跨用户变更返回 404。
- [x] 契约和生成 Client 一致，页面覆盖加载、空数据、成功和错误状态。
- [ ] 移除该示例不会破坏认证、OpenAPI 生成、迁移和 Harness。

### V0.3：运营与扩展能力

**整体状态：待规划，按真实产品需求选择子模块，不要求整包启用。**

**目标**：补充账号运营、通知、文件和长耗时任务等常见能力，同时保持基础模板轻量。

**范围**：

- 审计事件和管理操作记录：明确事件范围、敏感字段过滤、保留期限和查询权限。
- 邮件模板和通知：验证、重置等认证邮件已属于 V0.1；本阶段处理产品通知、计费通知与模板维护。
- 账户导出和删除：定义身份校验、数据范围、保留/删除例外及失败恢复后再实现。
- 文件上传：先确认对象存储服务、大小/类型限制、授权下载、清理和病毒检查要求。
- 异步任务：明确状态机、超时、取消、重试、幂等和失败处理；确实需要时再启用 Redis/队列。
- Python AI Worker：仅当具体产品依赖 Python 生态时采用；Go API 仍拥有身份、权益、用量和业务授权。
- 速率限制、Sentry/错误追踪及分析服务根据威胁模型、规模和供应商决策加入。

**前置依赖与决策门槛**：

- 各子模块有具体使用场景和规格；不能仅因为目录或 UI 已存在就实施。
- 文件、邮件、队列、监控服务需记录供应商、数据位置、密钥管理和本地替代方案。
- 需要额度或计费的子模块先定义自己的权益与用量规则；不得假定 V0.2 已建立通用计费模型。

**验收条件**：

- 用户只能访问自己有权访问的数据和任务结果；管理操作有审计证据。
- 异步任务在 Worker 重启或重复投递后仍符合状态和幂等规则。
- 上传对象不可被未经授权的用户读取；清理和删除行为可验证。
- 外部调用的超时、重试、限流、错误映射、凭据处理和用量归属有明确规格。
- 未启用可选模块时，核心开发启动和验证流程不要求其服务或密钥。

### V0.4：营销、内容与增长

**整体状态：部分页面已有，真实内容能力和 SEO 验收未完成。**

**目标**：使模板带有可替换的产品官网和基础内容入口，不将增长工具绑定为硬依赖。

**范围**：

- Landing、Pricing、博客和文档入口；营销定价内容集中配置。支付未启用时，Pricing 只作信息展示并明确不可购买；支付启用后才要求与后端有效套餐保持一致。
- SEO metadata、canonical、sitemap、robots、Open Graph 和结构化页面元信息。
- 博客采用仓库易维护的内容方案（例如 Markdown/MDX），经决策后实施；不默认引入完整 CMS。
- 默认语言和文案配置；多语言作为单独决策，不因页面框架自带能力就要求首版上线。
- 行为分析和推荐/联盟能力为可选项，明确同意、隐私和数据保留规则后再接入。

**前置依赖**：V0.1 和内容技术方案决策；若展示可购买的付费套餐，还依赖付费商业化阶段完成。

**验收条件**：

- 品牌名、域名、Logo、默认语言及外链等产品配置有明确单一来源，环境变量经校验。
- 页面移动端和桌面端可用，SEO 元数据和 sitemap 输出正确。
- 博客内容可在版本控制中审阅和发布；不存在时不要求运行 CMS。
- 支付未启用时，定价页明确说明价格仅供参考或计划尚未开放，不出现可完成购买的假流程；支付启用后，展示内容与有效套餐一致。
- 可选分析功能关闭时不阻断页面和核心产品流程。

### V1.0：模板产品化与可复制交付

**整体状态：待前述核心能力达到验收后规划。部署部分当前暂缓。**

**目标**：让使用者能判断能力边界、清理示例品牌、配置新产品并验证核心流程。

**范围**：

- 建立示例产品垂直切片，演示规格 → 契约/迁移 → Go API → Web → 验证的完整开发循环。
- 区分模板平台能力与示例业务，说明如何替换或移除示例。
- 建立功能矩阵、配置说明、架构图、开发指南、安全边界和故障排查文档。
- 梳理 feature flags：只用于真正可选的模块，服务端必须校验，默认配置明确；不得以布尔开关替代授权。
- 增加从干净副本初始化、种子数据和验证黄金路径的流程。
- 生产部署手册、部署自动化、备份恢复、告警和发布回滚仅在部署工作重新排期后纳入版本范围。

**前置依赖**：V0.1 完成；V0.2 示例切片及计划纳入首版的 V0.3/V0.4 能力完成；内容和配置来源稳定。

**验收条件**：

- 新副本可按文档完成配置、迁移、启动、注册、主要功能验证；不依赖原仓库历史状态。
- 示例业务可独立移除，移除后认证、契约生成、迁移和 Harness 仍可工作。
- 能力矩阵准确区分已实现、可选、演示占位和暂缓能力。
- 所有宣称可用的黄金路径有自动化或明确可重复的人工验证步骤。
- 若未完成选定环境中的真实部署、备份恢复和运行验证，不宣称生产就绪。

## 6. 明确暂缓与非目标

- **多租户、组织、成员邀请及 workspace**：首版单实例个人账户；若未来确定需要组织产品，再新增 ADR 和数据隔离设计，不能直接套入现有用户权限。
- **OAuth、MFA、SSO**：认证扩展项，当前不纳入核心路径。
- **部署平台和生产发布**：用户已明确暂缓。V1.0 的复制体验可先覆盖本地开发；恢复部署工作前需另行确定平台、环境、域名、密钥、数据库、邮件及备份要求。
- **支付、付费订阅和商业计费闭环**：因国内支付接入路径尚未确认，当前从近期版本移出。先完成不依赖支付的账户和示例业务；仅在支付服务可用性、商户准入、结算、退款、Webhook 和测试环境等前置条件确认后，再新建付费商业化阶段及对应 ADR。定价页面在接入前只作为明确标注的展示内容，不应伪装成可完成的购买流程。
- **供应商锁定决策**：Stripe、Resend、S3/R2、Inngest/Trigger.dev、Sentry、Vercel/Cloudflare 均未成为本仓库既定选择；相关决策应依据首发市场和实际需求形成 ADR。
- **多支付渠道、复杂税务、多币种、多地区合规账务**：首个商业版本稳定后再评估。
- **完整 CMS、通用工作流引擎、复杂 RBAC、全面数据分析平台**：不属于模板最小核心。
- **预先搭建所有抽象和基础设施**：无真实用例时不添加 Redis、对象存储、Worker、Python 服务或通用 Provider 注册体系。

## 7. 待做架构决策

这些问题不阻塞当前 CI/账户基础工作，但在相应里程碑开始前必须形成 ADR：

1. 支付提供方、商户准入与结算可行性、目标市场/币种、订阅周期、取消和退款政策（支付阶段启动前；当前暂缓）。
2. 生产邮件服务、发送域名、退信/重试及邮件模板维护方式。
3. 文件存储服务、访问方式、数据区域和生命周期策略（启动文件模块前）。
4. 队列技术和 Worker 运行方式（启动长任务模块前）。
5. 结构化日志、错误追踪、隐私分析和数据保留策略。
6. 部署平台、环境拓扑、域名与证书、密钥、备份恢复和发布回滚（恢复部署工作时）。
7. 模板品牌配置、语言范围和内容维护方式。

每项决策记录选项、取舍、影响和退出/迁移路径；不要把待决策事项写成已经确认的技术栈。

## 8. 项目执行规则

- 一次只实现一个可验收的垂直切片；完整经过规格、领域规则、OpenAPI、数据库迁移、服务端、Web 和验证。
- 安全、授权、幂等、错误状态和可观测性是功能验收的一部分，不作为上线前的补做事项。
- 不根据页面数量或脚手架目录判断完成度；以端到端行为和可复现证据判断。
- 每次计划变更更新本文件对应状态、验收证据、阻塞依赖和取舍理由；详细实现计划保存在功能规格中。
- 状态采用：`待规划`、`待开始`、`进行中`、`已完成`、`暂缓`。阶段部分完成时明确列出已完成与未完成项。
